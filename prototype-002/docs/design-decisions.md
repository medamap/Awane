# 設計決定の記録

## 背景と課題

### 初期実装（prototype-001）での課題
1. **同時アクセス問題**
   - あいり先生の初期化処理で、複数プロセスから同時にGetComponentしてセッション初期化すると競合が発生
   - 特にテスト時に顕在化しやすい問題

2. **将来の拡張性**
   - 当初は同一PC内の通信のみだが、将来的にネットワーク越しの通信も視野に入れたい
   - 言語の壁を越えたい（C#だけでなくNode.jsでもコンポーネント実装したい）

## 重要な設計決定

### 1. コンテキストベースの状態管理
**決定**: ステートフルなコンポーネントは、GetComponent後にCreateContextを呼び出して専用のコンテキストを作成する

**理由**:
- 各プロセスが独立したコンテキストを持てるため、競合を防げる
- コンテキストのライフサイクルを明確に管理できる
- 簡易的なロック機構（1分間のファイルロック等）も実装しやすい

**例**:
```csharp
var airi = GetComponent<IAiri>();
var airiContext = airi.CreateContext("ワーキングディレクトリ");
if (airiContext.IsAlreadyInitialized) return;
if (airiContext.IsNotGitHubRepositoryTop) return;
```

### 2. gRPC + Adapter Patternの採用
**決定**: 簡易版（Named Pipe + JSON-RPC）ではなく、gRPCベースの実装を選択

**比較検討の結果**:
- 簡易版: 実装は簡単だが、ネットワーク対応が困難
- gRPC版: 初期実装は複雑だが、将来性が高い

**理由**:
- 将来的なネットワーク対応を見据えて
- 多言語対応が確実（Protocol Buffersによる型定義）
- ストリーミング、認証、エラーハンドリングが組み込み済み
- 既存コードに縛られず、クリーンな設計で始められる

### 3. 既存コードを捨てる決定
**決定**: prototype-001の実装を参考程度に留め、prototype-002では新規実装

**理由**:
- 既存コードの流用で良い結果が出た試しがない（経験則）
- 新しいアーキテクチャに合わせて設計し直す方が結果的に早い
- 技術的負債を持ち込まない

### 4. 通信方式の段階的拡張
**決定**: 同一プロセス → 同一PC → LAN → WANと段階的に拡張する設計

**実装方針**:
```
同一プロセス: 直接参照（C#のみ）
同一PC: Unix Domain Socket
LAN/WAN: gRPC over TCP/HTTP2
```

**理由**:
- 一度に全てを実装するのは複雑すぎる
- 各段階で動作確認しながら進められる
- 用途に応じて最適な通信方式を選択できる

## 議論の要点

### 多言語対応の範囲
- **当面のターゲット**: C#とNode.jsに絞る
- **理由**: この2言語でgRPCの一級サポートがあり、実装が現実的
- **将来**: Protocol Buffersベースなので、他言語への拡張も可能

### あいり先生のNode.js実装
- **可能性**: Awaneの設計上、言語を問わずコンポーネント実装可能
- **実装方法**: gRPCサーバーとしてNode.jsプロセスを起動し、C#から呼び出す
- **メリット**: Node.jsのエコシステム（npm packages等）を活用できる

### セキュリティとパフォーマンス
- **ローカル通信**: Unix Domain Socketで高速化
- **ネットワーク通信**: TLS暗号化、認証機能を利用
- **接続プーリング**: チャンネルの再利用でオーバーヘッド削減

2. **テスト戦略**

   - 同時アクセスのテストケース作成

3. **運用考慮事項**
   - モニタリング、ログ、デバッグ機能
